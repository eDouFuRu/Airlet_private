# 工位充电岛 · 2.5D 薯队长与红薯钟

## 296 版：合唱歌曲的歌词匹配（2026-09-09）

**《All for Joy》一句歌词都没有，《加油》的歌词整体晚三四秒。** 两件事是同一个根因。

先说清楚歌词是怎么来的：**不是从播放器接的**。macOS 的 MediaRemote 只给标题、艺人、专辑、时长、进度，**没有歌词字段**，任何应用都拿不到网易云自己的歌词流。所以是现从网络下载 LRC，两个源——网易云公开接口与 LRCLIB，时间轴则由本地按 `elapsed + (now − lastUpdated) × rate` 推算，每 100ms 打一拍。

网易云 Mac 版经 MediaRemote 上报的元数据**只有主唱**：`title="加油！" artist="林俊杰" album="100天" duration=227.64`。而唱片库里这首歌署名是 `林俊杰 / MC HotDog 热狗`。`artistMatches` 要求两侧**相等**（只允许剥离 `David Tao ` 这类前置拉丁署名），于是**所有合唱曲目一律判不匹配**。《All for Joy》在网易云（`陶喆 / 关诗敏`）和 LRCLIB（`David Tao 陶喆 feat. Sharon Kwan`）都存在，两边都只栽在这一项上，因此一句都没有。

《加油》的"延迟"是同一道闸门的次生结果：网易云那条被拒后退到 LRCLIB，捡到一条署名只写"林俊杰"的转写。它与网易云是同一录音（时长同为 227.64），但**时间轴整体差三四秒**——"最近你好吗"网易云记 16.10、这条记 20.06；"发现你爱的人到处跑"记 41.97 对 44.77。**不是时钟 bug，是挑错了版本。**

改法是把艺人判定从"相等"换成"**主艺人一致**"：把双方署名按 `/ & , ; 、，（）` 与 `feat / ft / featuring / with / vs` 拆成 credit token，任一方的首个艺人出现在对方列表里即通过。方向是双向的——Apple Music 有时反过来发完整署名而 LRCLIB 只写主唱，单向包含会把这种情况判死、反而制造新的"没歌词"。**方括号不算分隔符**：`[PT80]`、`[Explicit]` 是发行标记不是署名，`林俊杰[PT80]` 必须继续判不匹配（本仓库原有的一条断言，改动初稿曾把它弄挂）。放宽是安全的，因为**标题精确、专辑精确、时长 ≤1 秒三道闸门一律没动**，"不借用错误时钟"的原设计意图不受影响；`artistMatches` 也只有两处调用点。

**歌词源顺序保持播放器驱动，没有改。** 中途我曾把"中文元数据曲目一律优先网易云"加进来，理由是《加油》在 LRCLIB 上有互相冲突的多版本——**这个理由站不住，已回退**。两个 bug 的修复完全来自 artist 那一处：网易云播放本来就是 netease 优先，换序只影响非网易云播放器。

回退的依据是实测而非推理：拿 18 首中文歌同时查两个源，初版探针报出 3 条"时间轴不一致"（差 1.56s / 4.28s / 18.54s），逐条核对后**全是探针自身的 credit 过滤漏了 `监制` / `OP` 造成的假阳性**——把署名行的时间戳当成了首句。真实的不一致一条都没有。剩下"LRCLIB 未命中 8/18"这条也不可靠：查询用的是网易云的专辑名，而 LRCLIB 的 `/get` 要求专辑精确匹配，等于给它上难度，何况生产代码还有第三层 titleOnly 兜底比探针宽容。

所以现状是：网易云播放 → 网易云优先；QQ / 酷狗 / Spotify / Apple Music → LRCLIB 优先、网易云兜底（与 294 及之前一致）。**LRCLIB 同一录音存在多份冲突转写的问题未解决**，非网易云播放器遇到时仍可能偏几秒；把它记为已知边界，等真要接 QQ / 酷狗的官方源时再一并处理，而不是现在用一个拿不出数据支撑的全局偏好去盖住它。

真实网络回归（`run-netease-live.sh --live`，用播放器实际上报的元数据）：《加油！》命中 64 句、首句 **16.1s**；《All for Joy》命中 **56 句**、首句 16.52s；既有的《远走高飞》仍为 34 句、25.45s。三首都验了"**刚好在该句之前不显示、到点显示、一秒后仍是该句**"——这正是刘海渲染时调用的 `document.line(at:)`。

自动化门：SwiftPM **567 项**（+3）、服务 harness **97 项**、歌词源 harness **37 项**（+1）、本地化审计通过（948 条，本轮未新增文案）。

⚠️ **顺带修正三处历史文档失准**：上一版记的"build 292"实际是 **294**（验收轮次里多次递增未回写文档）；"SwiftPM 533 项"实际改动前为 **564**；"本地化 937 条"实际为 **948**。本节数字以本轮实跑为准。

**真机验收由用户亲耳完成**：Build 296 装机后用户播放两首歌，确认"**这两首歌对齐了**"。这一条不是程序化取证——网易云是 Electron 应用、不暴露辅助功能树，其窗口又在另一个桌面空间，程序化驱动会打乱用户的工作区，所以"歌词是否与人声同步"从一开始就只能由用户判定；自动化侧能证明的仅是"匹配到了权威源那一版、且在正确秒数给出正确句子"。

**仍未取得的证据**：**非网易云播放器一个都没有测过**。QQ 音乐 / 酷狗 / Spotify / Apple Music 走的是 LRCLIB 优先那条分支，本轮既没有安装也没有播放，上面那条"LRCLIB 多版本冲突"的已知边界因此仍是推断而非实测（用户明确表示"别的播放器下次我安装了再说"）。

## 292 版：充电提示改用系统提示外形 + 剪贴板按原格式暂存（2026-09-08）

**充电提示从来没有留白，而且暂存区一有文件就不出现了。** 两件事是同一处代码的两面。插拔电源的提示写在 `closedHeader` 的 battery 分支里，而 `closedHeader` **只在小岛收起时使用**；暂存区非空时 `open()` 会落到暂存页，暂存页通过 `NotchOpenHoldCenter.begin(.pinnedPage)` 把小岛钉住展开，而 `close()` 又不重置 `currentView`。于是提示所在的分支根本不渲染，`BoringViewCoordinator` 那个 3 秒定时器照常把 `expandingView.show` 清掉 —— 提示无声地过去了。宽度那边则是硬编码 `return 640`，加上文字与电池图标各自 `frame(maxWidth: .infinity)` 顶到两边。

改法是让它穿上系统提示的外形：新增 `PowerNoticeRow`（放在 `InlineHUD.swift`，与 `InlineHUD` / `SystemHUDRow` 并列），几何常量逐字复用那两者，宽度交给 `SystemHUDLayout` 推导，因此**跟随「内嵌 / 默认」设置**并且展开态也能渲染。只复用**布局**，不复用事件通道：`HUDStateManager` 要求辅助功能授权，把充电提示接上去会让没授权的用户彻底看不到提示。出现条件按用户指定收敛为 `showPowerStatusNotifications && hudReplacement` —— 关掉「替换系统提示」才不提示，暂存区状态与展开与否都不再参与。

**「暂存剪贴板图片」会把 `.md`、`.swift` 变成 `.png`。** 在访达里复制一个文档，剪贴板上除了文件 URL 还带一份**该文档图标的位图**，而导入代码先问「有没有图片」，于是拿到图标、重新编码成 PNG、以 `Clipboard-<日期>.png` 落盘 —— 原文件的字节、扩展名、文件名全丢。判定规则抽成 `Interaction/Core/ClipboardStagingDecision`：**先文件后位图**，文件按原名原字节复制，只有纯位图才走 PNG。后台自动导入与手动按钮共用这一条规则，否则开着自动导入时同一个 bug 依旧（而且是无人点击就自己发生）。按钮更名为「暂存剪贴板文件」。

**拖着文件靠近刘海现在总是展开暂存页。** 之前暂存区为空时会落到媒体页，手上拿着文件却无处可放。第一版改在 `GeneralDropTargetDelegate.dropEntered` 里切页，**实测无效**：小岛收起时 `ignoresMouseEvents = true`，此刻它根本不是拖拽目标，等悬停机把它展开、该标志翻回来时指针早已在窗口内部，`dropEntered` 不会补发。改为在 `open()` 里直接判断「手上是否拿着文件」：`NSEvent.pressedMouseButtons` 有左键按下 **且** `NSPasteboard(name: .drag)` 里读得到文件 URL。按键那一半是必需的 —— 拖拽剪贴板在拖完之后仍保留内容，只读它会在拖拽结束很久后仍报告有拖拽。这条分支排在 `openShelfByDefault` 之前，所以那个设置继续只管空手悬停，不需要再加开关。

**暂存区支持复制 / 剪切 / 粘贴。** ⌘C / ⌘X / ⌘V 需要事件监听：小岛按硬约束**不抢键盘焦点**，响应链根本收不到按键，而事件监听要辅助功能授权 —— 未授权时快捷键静默不存在，不弹窗不报错。监听**只在指针停在暂存区上时安装**，离开立刻卸载：全局按键监听看得见所有应用的键盘，长期挂着会让用户在别处按的 ⌘C 悄悄把剪贴板换成暂存区选中项。剪切复用 10 秒撤销窗口（新增 `.cut` 类型），先写剪贴板再移除，文件在窗口期内不删 —— 否则剪贴板里会是一串指向已删除文件的 URL。

右键菜单是零权限的保底路径。空白处那一份**不能用 SwiftUI 的 `.contextMenu`**：弹出它需要窗口接管这次点击成为 key 窗口，而小岛永远不会 —— 实测右键毫无反应。改用 `ShelfBackgroundMenu` 手搓 `NSMenu` + `popUpContextMenu`，与暂存条目本身的菜单同一套路子（那个菜单当初就是为此手写的）。它对 `hitTest` 返回 nil、只从窗口事件流里挑走右键，因此左键、拖拽、投放照常穿透到下层。这份菜单恰恰在**暂存区为空**时最要紧 —— 那时没有条目可右键，而粘贴正是用户唯一想做的事。

另外：「清空位置」磁贴现在真的可点（点击清空全部槽位，全空时置灰），此前只是个拖拽落靶；歌词颜色默认改为跟随专辑封面。

**「启用专辑封面背景模糊」名不副实**：`lightingEffect` 只控制叠在封面**上层**的一层柔光，真正的背景模糊视图 `albumArtBackground` 定义了却从未被调用，是死代码。已删除死代码，开关更名为「专辑封面辉光」。

自动化门：SwiftPM **533 项**（+12）、服务 harness **97 项**（+12，新增 `ShelfChordHarness` 对真实 `ShelfKeyboardChords` 做授权故障注入）、本地化审计通过（937 条词条，仅追加不排序）、签名安全 30 项。

真机验收（Build 292）：七项全部实测，逐项证据与边界见 `SETTINGS-VERIFICATION.md`。几个关键点：清空位置用的是**真实鼠标点击**而非 `AXPress`；充电提示改用能量模式触发真实电源事件（与插拔电源同一条 `notifyImportanChangeStatus` 路径），在**暂存区有文件且小岛钉住展开**的原缺陷场景下确实画出来了，默认模式收起态的帧 `@602,0 308x60` 与音量 HUD **逐点相同**，内嵌模式两者**高度与中心相同**；⌘C/⌘X/⌘V 含多选、剪切撤销、以及「指针离开暂存区后不劫持剪贴板」的反证。**真实插拔电源也已取证**：用户本人插拔电源线，后台逐秒轮询记到 `Not charging` / `Charging battery`，默认模式帧 `@602,0 308x60`、内嵌模式帧 `@559,0 393x32`，与音量 HUD 对应模式**逐点相同**；其中一次拔电发生在小岛展开时，提示照样画了出来。**像素级留白也实测了**：等帧稳定后截同一区域逐列扫亮度，充电提示左 18.0pt / 右 16.0pt，音量 HUD 左 20.5pt / 右 17.0pt，差 ≤2.5pt 来自字形轮廓 —— 旧实现是 0 留白 + 640 宽，这条直接被推翻。未授权辅助功能的降级，除了 `ShelfChordHarness` 对真实生产类做故障注入，还在**一个真正没有授权的全新 bundle 里跑了真实 API**（`AXIsProcessTrusted()=false`、`setActive(true)` 后 `isListening=false`，无弹窗无报错），因此不必去吊销本机授权。

## 291 版：媒体槽位拖拽修复 + 暂存区一键清空（2026-09-08）

**媒体控制的拖拽从来没生效过。**「设置 → 媒体 → 媒体控制」上写着「拖动按钮移动或交换位置；拖回按钮库即可移除」，实际拖动毫无反应，只能在按钮库里逐个点击按顺序填。根因不在数据层：拖源与拖靶的类型标识符逐字相同，reducer 有充分单测，而点击路径与拖放**共用同一个 `apply(_:to:)`** —— 点击能用恰好证明数据层完好。真正的原因是**容器**：这块 UI 嵌在 `Form { }` 里，而整个设置窗口加了 `.formStyle(.grouped)`，macOS 会吞掉其中的 `.onDrag`/`.onDrop`。

这个坑本仓库早就踩过并绕过了 —— 快捷工具页的拖动排序就是为此写的纯 AppKit 方案。本轮把它与载荷无关的部分抽成 `Interaction/LocalReorderDragRuntime.swift`，两个域各自套一层类型化薄包装：

- 运行时**不是泛型**。Swift 不允许泛型类型拥有 static 存储属性，`Runtime<Payload>.shared` 根本编不过；泛型 `NSView` 子类在 ObjC 运行时侧也不稳。改为把载荷擦除成 `Any`，只在两个 `NSViewRepresentable` 边界各做一次 `as?`，另一个域的载荷降级失败即拒绝投放。
- `ToolReorderNativeBridge.swift` 退化为工具专用薄包装，**公开字段签名原样保留**，因此 `SystemToolsPage.swift` 零改动。

工具页的手柄是独立小把手，与点击区不重叠；媒体这边用户要拖**图块本身**，而图块还得响应单击选中、右键菜单、右上角 ×。AppKit 的 `hitTest` 一旦让手柄接管，同位置的 SwiftUI 手势识别器就再也收不到事件 —— **被动透传做不到**，必须在手柄里显式重建：单击走 `onClick`，右键走 `menu(for:)`，× 靠 `excludedTopTrailingCorner` 在命中测试里挖一个洞。这个洞写成**尺寸**而不是矩形是刻意的：写矩形就要调用方自己把 SwiftUI 的 y-向下翻成 AppKit 的 y-向上，翻错就是一个按不动的按钮。

**暂存区新增一键清空。** 刘海外侧右上方原有一个悬浮「收起小岛」按钮，其下方再加一个「清空暂存区」，两者同尺寸（直径 22 → 26），**各自处在小岛展开态上下半区的中轴位置**，因此关于横中轴天然对称 —— 对称性是构造出来的，不是算出来的。锚点必须读**运行期的 `visibleFrame.height`**：暂存页展开高度是运行期结果，且展开动画中逐帧变化，用编译期常量会让两钮在动画中错位。

清空是破坏性操作，复用暂存区现有的 10 秒撤销：点一下即清空，出现「已清空 · 撤销」小条，窗口期内不碰临时文件，到期才真删。暂存区为空时清空钮变暗禁用而**不隐藏** —— 隐藏会让收起钮孤零零挂在上半区，破坏对称观感。

同时删掉了 `topInset` 常量：ContentView 直接调 `topEdgeOffset(visibleHeight:slot:)`，视图层不再自己做任何加减。288 版那个「绘制圆比命中圆低 11pt」正是因为 ContentView 手写了 `topInset + diameter/2`。

`windowSize.width` 由 742 增至 750（公式自动跟随 `diameter`）。

真机验收（Build 291）：见 `SETTINGS-VERIFICATION.md`。**几何与清空/撤销已验；依赖真实鼠标的拖拽与命中区各项尚未验收**。

## 290 版：红薯钟收起态提示可关闭（2026-09-08）

新增「设置 → 红薯钟 → 收起状态 → 在收起的刘海上显示倒计时」，默认开启。关掉后计时期间刘海不再显示图标与剩余时间，宽度也从 +88 缩回正常值；**计时本身不受影响**，照常推进、照常按时结算，专注完成提醒也照旧。

实现上把 `baseClosedWidth` 与 `closedHeader` 两处原本各自判断 `resting` 的分支收敛到同一个 `showsRestOnClosed` 属性。这两条是手写的平行 if/else 链，只改一条就会出现「壳撑宽了 88 点但里面什么都不画」；共用属性让它们在语法上就无法不一致，比补一条单测更硬 —— 288 版的悬浮按钮正是栽在同类问题上（绘制与命中各算各的，错开 11pt）。

**一个行为变化**：`closedHeader` 是优先级链，红薯钟排在媒体前面。关掉这个开关后计时期间刘海不再被红薯钟占用，所以**同时在放音乐时闭合态会显示媒体两翼**，宽度按媒体那套算。这是刻意的 —— 等同于「计时提示不存在」，刘海回到它本来该有的样子。

真机验收（Build 290）六项全过，见 `SETTINGS-VERIFICATION.md`。

`openShelfByDefault` 默认值 false → true，用户仍可在「设置 → 文件暂存 → 通用」关闭。两处使用点都带 `!isEmpty` 闸门，所以空暂存区不会改变落地页 —— 这个开关只在真有东西暂存时才起作用。已显式关过的用户存着 false，不受影响。

## 288 版：悬浮收起按钮命中错位修复（2026-09-08）

Code Review 自查发现的坐标基准混用：`.overlay(alignment: .top)` 对齐的是子视图**顶边**，而 y 偏移却按「中心偏移」写成 `topInset + diameter / 2`，于是绘制圆比命中圆恒定低 11pt。后果是按钮视觉下半截落在命中区外、点击**穿透到后面的应用**，上半截则悬在桌面上什么也没画却吞掉点击。因为小岛还会被「点击外部」这条路径顺手收起，现象被掩盖成「按钮时灵时不灵」。

之所以 518 项单测全绿也没拦住：`NotchAccessoryControlTests` 那条断言用同一组常量既当期望值又当被验证公式，恒为真，够不着 `ContentView` 的实际偏移表达式。这条测试**本轮未加固**，下次再动这个偏移量它照样拦不住。

真机验收（Build 288）：AX 实测绘制帧 `@1287,1092 22×22`，与 `NotchAccessoryControl.rect` 逐点重合；点可见圆上缘/圆心/下缘 frontmost 均不变且小岛收起（被窗口捕获），同一行右下方角 frontmost Finder→Valos（穿透）—— 圆形判定与「方角不吃别人点击」同时成立。

同轮还修了：撤销窗口期内退出应用会把临时文件变成孤儿、`init` 内 `didSet` 不触发导致 `addedAt` 回填不落盘、剪贴板同图重复复制堆条目、主线程同步读盘解码截图、清理器 `start()` 非幂等、popover 保持上限 30s 过短、悬停切标签页缺过渡动画。另把到期「真删」的范围文案改准确：闸门是 `isTemporary`，去背景/转格式/合成 PDF/压缩产物同样会被真删，不止截图录屏剪贴板。

## 287 版：拖出误删修复与暂存区到期清理（2026-09-08）

**「拖回小岛也被删」的根因**是暂存区左侧的「System Share Menu」磁贴无条件接收拖放（`FileShareView`），既误触发一次分享，又让拖拽源以为文件已送达。现已加上与暂存列表一致的自拖拽守卫，并在拖拽源侧补一道结构性兜底：**落点落在本应用任一可见窗口内一律不算送达**，今后再有落点忘写守卫也不会造成删除。

**拖到聊天框/网页却没插入也被删**这一类无法根治：AppKit 只告诉发起方「某个接收方的 `performDragOperation` 返回了 YES」，Chromium 系窗口在整窗范围都会答应，落在哪个 DOM 节点上则看不见。实测拖到 Valos 侧栏（明显不是输入框）确实被判为已接收。因此改为**让判错可撤销**：移除条目后临时文件不再立即删除，暂存页出现 10 秒的「已移出 · 撤销」小条。

顺带修掉一个一直存在、把功能变成空转的缺陷：`TemporaryFileStorageService` 用 `NSTemporaryDirectory()` 的 `/var/…` 前缀去比对书签解析出的 `/private/var/…` 路径，守卫恒不通过，**暂存区的临时文件从来没有被删除过**。现由 `TemporaryFilePathGuard` 归一化后比较（并要求分隔符，避免 `/T` 误配 `/TEvil`）。

拖拽源掩码固定为 `.copy`，不再提供 `.move`：以「复制后删原件」实现移动的目标会把暂存文件搬走，条目随后被书签失效清理顺手删掉，现象和拖出移除一模一样却是另一条路径。因此恒真的「拖出时复制」开关一并移除。

**新增到期自动清理**：`ShelfItem` 增加可选 `addedAt`，每个文件从进入暂存区起独立计时，可选不清理 / 12 小时 / 1 天 / 3 天 / 1 周，默认 1 天。真删的范围是**应用自己在临时目录里生成的所有产物**：截图、录屏、剪贴板图片，以及去背景、转格式、合成 PDF、压缩生成的文件，还有拖入时只拿到裸数据（没有真实文件 URL）而由应用写盘的副本；只有从访达拖进来、仍能定位到原文件的条目才是到期只移除条目，磁盘原件不动。判定闸门是 `ShelfItem.isTemporary` 加 `TemporaryFilePathGuard`（必须落在系统临时目录内），不是「是不是截图」。

## 286 版：按住移除组合键不再改动选中集（2026-09-08）

移除组合键含 ⌘，而 ⌘ 同时是暂存区的多选键，于是按住 ⌥⌘ 去拖某一项会先把它加进选中集，连带把此前选中的文件一起拖走并移除。现按住完整组合键时点按不再改动选中集，回到 macOS 标准语义：**拖未选中的项只拖它自己，拖已选中的项拖整组**。单独按 ⌘ 的多选不受影响。

判断「组合键是否按下」的逻辑收敛到 `Interaction/ShelfDragRemovalChord.swift`，点按路径与拖拽路径共用同一份，避免两处各自采样得出相反结论。真机验证了两半契约：先选中 A 再 ⌥⌘ 拖 B，只有 B 送达并移除、A 原样保留；⌘ 多选两项后 ⌥⌘ 拖其中一项，两项一起送达并清空暂存区。

## 285 版：拖出即移除的组合键可选（2026-09-08）

暂存区「拖出即移除」的触发键从写死的 ⌘D 改为设置里可选，默认 **⌥⌘**。改用纯修饰键组合是因为含字母的组合会被放置目标当成自己的菜单快捷键——实测拖进访达时访达执行了 ⌘D「复制」，把放置搅黄；⌘A 更是几乎所有 App 的「全选」。可选项为 不使用 / ⌥⌘ / ⌃⌘ / ⌘D(legacy)。

同时修掉两个真机暴露的缺陷：一是**必须先松键再松鼠标**，根因是 `ignoreModifierKeys` 返回 `false` 让 AppKit 用 ⌘ 把拖拽操作强改成 `.move`，只接受 `.copy` 的聊天输入框会直接拒收；二是**拖动途中才按下的组合键不算**，原先只在拖拽开始采样一次，现改为在按下鼠标 / 拖拽开始 / 指针移动 / 放手四处锁存。

## 数据迁移与权限

应用 Bundle ID：`com.dongfengrui.NotchIsland`。辅助服务：`com.dongfengrui.NotchIsland.XPCHelper`，与参考应用独立。

新存储键为 `notchIsland.potatoSession.v2`。首次启动仅在没有 v2 快照时导入旧 `notchIsland.restSession.v1`：每次历史休息对应一颗库存，旧的一分钟运行/暂停状态继续恢复，旧快照和旧成长消费记录不被重写，便于原型回退。回退后产生的新 v1 记录不会再次导入已有 v2。

计时核心负责一次结算并原子保存，UI 只负责展示；可见性登记按窗口区分，收获动画仅交给实际挂载、展开且可见的小岛页，隐藏和锁屏先关闭全局交付开关。完整快照损坏不会被当作旧 v1 再次导入。

进入小岛不主动申请日历或摄像头权限。镜子按使用启动，隐藏时停止；日历与提醒分别申请。HUD 设置与系统按键拦截器共享主应用的辅助功能状态，区分未授权、启用、暂时停用和启动失败。没有真实可见面板时停止接管，隐藏后旧按键任务与迟到硬件回复不能重新弹出。启动时读取当前 GUI 会话，未知或未激活会话保持关闭；唤醒不清除锁屏/会话门控。恢复时沿用用户开关意图。系统授权弹窗语言由 macOS 决定。

HUD 提示独立于休息计时和音乐，最后一次提示约 2 秒后恢复。默认样式使用 28 点显示行，内嵌样式使用摄像头两翼；闭合时背光标题与错误摘要采用短文案，展开、悬浮提示和辅助功能标签保留完整说明。HUD 设置中的只读诊断可选中、复制，包含进程路径、签名、AX、tap、最近 20 条媒体事件及最后一次硬件实际回读/失败信息。
